# Streaming re-sign — signing very large IPAs on-device

## Problem

The current pipeline extracts **every** zip entry to disk by reading the whole
file into memory first (`IPAReader.ReadFile` → `io.ReadAll`, then `os.WriteFile`).
That is fine for a few hundred MB, but an app of several GB usually carries one
or two very large individual assets (a video, an ML model, packed game data).
Reading a >1.5 GB entry into a single buffer trips iOS jetsam and the app is
killed. Peak memory therefore scales with the **largest single file**, which is
unacceptable for a 4 GB target.

Signing cost itself is **not** the issue: it tracks the number and size of
Mach-O binaries (page hashing + CMS), not the IPA size. Measured on device
(iPhone 16 Pro Max): 3 MB → 0.30 s, 150 MB → 3.0 s, and 134 MB signs *faster*
than 102 MB because it has fewer binaries. The bottleneck to fix is **memory
during I/O**, not CPU.

## Design: two-pass streaming, zip → zip

An IPA is a zip. Signing rewrites only a small set of entries — `Info.plist`,
the Mach-O binaries, `_CodeSignature/CodeResources`, `embedded.mobileprovision`,
optional icon PNGs. Every other entry (the bulk: images, video, `.car`, data) is
**unchanged** and only needs its hash computed for `CodeResources`.

So we never fully "extract". We stream the input zip to the output zip in two
passes, with a hard rule: **no entry is ever held whole in memory.**

### Pass 1 — hash & plan (streaming, bounded memory)

Walk every entry of the input zip. For each:

- Compute its uncompressed SHA-1 + SHA-256 by streaming the decompressed bytes
  through the hashers with a fixed 64 KiB buffer (`io.CopyBuffer`), never
  `io.ReadAll`. Record `{path → hashes}` in the `CodeResources` seal (a few
  hundred bytes per file; 10 000 files ≈ 1 MB total).
- If the entry is a **Mach-O** (magic `0xFEEDFACF` / fat), it will be re-signed:
  stream it to a small temp file, compute page hashes (already chunked, 4 KiB),
  build the code-signature superblob, and record its cdhash for the enclosing
  bundle's seal. The temp file is deleted right after Pass 2 writes it.
- `Info.plist`, `CodeResources`, and `embedded.mobileprovision` are noted for
  regeneration, not sealed from the input.

Peak memory here is: 64 KiB I/O buffer + per-binary page-hash arrays
(`fileSize/4096 × 32 B`; ~8 MB even for a 1 GB binary) + the seal dict (~MB).
Independent of IPA size.

### Between passes

Assemble the modified `Info.plist`, the new `CodeResources` from the collected
hashes, each Mach-O's signature, and the (silent) provisioning profile.

### Pass 2 — write (streaming, raw-copy)

Walk the input zip again, writing the output zip:

- **Unchanged entry → raw copy.** Use `zip.File.OpenRaw` → `zip.Writer.CreateRaw`
  to copy the already-compressed deflate stream **verbatim** — no decompress, no
  recompress. This is the single biggest time saver on the asset bulk.
- **Mach-O → signed version** from its temp file (signature injected by
  streaming the binary up to the insertion point, then appending the superblob).
- **`Info.plist` / `CodeResources` / profile → the regenerated bytes.**

Peak memory in Pass 2 is again just fixed buffers.

## Nested bundles & signing order

Frameworks (`*.framework`), app extensions (`*.appex`), and watch apps
(`*.app`) are **independent bundles**: each has its own main Mach-O and its own
`_CodeSignature/CodeResources`. A parent's `CodeResources` seals its children's
*signed* content, so signing is a post-order recursion:

```
sign(bundle):
  for child in bundle.nested:  sign(child)      # deepest first
  sign each Mach-O in bundle
  build bundle CodeResources   (seals children + resources)
  sign bundle main executable  (embeds the sealed CodeDirectory)
```

The two-pass walk is applied per bundle; the top-level Payload zip is the outer
container whose Pass 2 raw-copies everything except the entries the recursion
marked as rewritten.

## Edge cases (must handle)

| Case | Handling |
|---|---|
| **Symlinks** inside frameworks (`Current` → `A`, `.dylib` → `Versions/…`) | Zip stores them as entries with the symlink mode in external attrs. Raw-copy them verbatim; **do not** follow/hash the target — the seal records the link, matching Apple's tooling. |
| **`Assets.car`** | A normal resource: streamed-hash + raw-copy like any asset. `DeleteAssetsCar` simply omits it in Pass 2 and from the seal. |
| **Zip64** (>4 GB total, or >4 GB entry, or >65 535 entries) | Go's `archive/zip` reads and writes Zip64 automatically; `CreateRaw` preserves it. No special code. |
| **Deeply nested signatures** (framework inside appex) | Falls out of the post-order recursion; depth is unbounded. |
| **Entitlements** | Taken from the provisioning profile (`entitlements.Extract`), embedded per-binary in the CMS; unchanged from today. |
| **Already-signed input** | The old `_CodeSignature` and any stale signature load-command are dropped/rebuilt, not sealed. |
| **Non-deflate stored entries** | `CreateRaw` copies `Store` entries verbatim too. |

## Properties vs today

| | Today | Streaming |
|---|---|---|
| Peak RAM | scales with largest file (OOM at ~1.5–2 GB) | **~tens of MB, size-independent** |
| Disk | ~3× IPA (full extract + output) | **~2× IPA** (assets never extracted; temp for binaries only) |
| Asset handling | decompress + recompress | **raw byte copy** |
| Binary signing | sequential | parallel across cores |
| 4 GB IPA | unsafe | safe, ~10 s (I/O-bound copy of 4 GB + parallel binary signing) |

## Import-side companions

- Download **streamed & resumable** (already `dio` on the app side) with a
  progress bar.
- **Pre-flight disk check**: require ~2× the IPA size free before starting; fail
  with a clear message instead of a mid-run crash.

## Implementation map

- `ipa/archive/reader.go` — add streaming `OpenRaw`/`OpenFile` accessors; keep
  `ReadFile` only for small control files (Info.plist, CodeResources).
- `ipa/archive/writer.go` — add `CreateRaw` passthrough.
- `ipa/pipeline/resign.go` — replace the extract-all loop with the two-pass
  walk; recurse per bundle in post-order; temp only the Mach-O binaries.
- `plist/coderesources/*` — already streams hashing (`io.Copy`); feed it from
  the Pass-1 walk instead of on-disk files.

> Note: this is the **opposite** of an in-memory rewrite. We stream *more* to
> disk and hold *less* in RAM — which is exactly what makes multi-GB IPAs
> possible on iOS.
